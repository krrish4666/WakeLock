=================================================
WAVELOCK: PRODUCT ARCHITECTURE & TECHNICAL DESIGN
=================================================

1. Project Overview
-------------------
WakeLock is an accountability and productivity platform built over Telegram that structurally enforces waking up on time. It achieves this by locking a user's virtual funds inside an "Accountability Plan". If the user fails to verify their attendance within a dynamic, randomized time-window every morning, an automatic, non-refundable financial penalty is deducted from their locked funds. The system heavily leverages asynchronous task pipelines, an immutable ledger, and Telegram UI to create a strict, engaging financial habit-tracker.

2. Core Concept and Idea
------------------------
- Accountability Model: Users declare a financial commitment by locking funds for a chosen duration (e.g., 7 days).
- Financial Penalty Logic: A daily penalty is calculated mathematically (Total Locked / Duration). Missing a single alarm permanently deducts this amount from the user's funds.
- Randomized OTP Verification: Simply waking up and clicking a button is too easy to bypass. Instead, an OTP (One-Time Password) is dispatched dynamically at a random minute during a 10-minute drop window, forcing the user to stay awake and alert to receive and enter it.
- Why it Exists: The system attempts to cure chronic oversleeping and poor morning habits by attaching genuine, automated financial consequences that cannot be snoozed, dismissed, or ignored.

3. System Architecture
----------------------
The system is built as a highly decoupled backend consisting of four primary components:
- FastAPI Backend: Acts as the core interface handling the database lifecycle, dependency injection (via AsyncSession), and application orchestration.
- Telegram Bot Interface: Managed by python-telegram-bot. It consumes raw text payloads, parses command headers (/alarm, /plan), and funnels inputs into the discrete service-layer logic.
- Celery Task Scheduler: Accompanied by Celery Beat and a Redis broker. It autonomously sweeps the database for alarms, triggers Telegram warnings, calculates randomized OTP drops using `apply_async(eta=X)`, and eventually sweeps for expired/failed verifications.
- Database Layer: Handled by asynchronous SQLAlchemy and Alembic for strict relational constraints.
The interaction maps cleanly: the Telegram UI sets the DB state; Celery autonomously reads the DB state to orchestrate the morning flow; and Celery modifies the DB state if the user fails to interact with the Telegram UI in time.

4. Key Domain Models
--------------------
- User: Identifies the Telegram user via `telegram_id`.
- Wallet: Maintains the fast-retrieval cache of `total_balance`, `locked_balance`, and `available_balance`.
- WalletTransaction (Ledger): An immutable, strictly-append-only record of every single financial movement (calculating `balance_after` atomically).
- AccountabilityPlan: Defines the overarching schema for a user's commitment (duration, total locked amount, and calculated per-day penalty).
- WakeSession: The state machine representing a purely isolated daily morning attempt. Transits strictly from `PENDING` -> `OTP_ACTIVE` -> `VERIFIED` or `FAILED`.
- UserPreference: Decoupled from the Plan, this explicitly stores the user's configured `alarm_time` and `buffer_minutes`.

5. Wallet Ledger Architecture
-----------------------------
To prevent silent financial bugs (such as funds bypassing the wallet or disappearing without a trace), the system rejects simple "balance update" operations. Instead, it utilizes an Append-Only Ledger system.
Every single transaction (Deposit, Plan Purchase, Penalty, Withdrawal) is logged using a centralized `WalletService.record_transaction()` helper. This creates an auditable paper trail ensuring that the arithmetic sum of the `WalletTransaction` types statically equals the live numbers mapped to the `Wallet`.

6. Alarm and Verification Flow
------------------------------
1. Alarm Trigger: Celery Beat scans `UserPreference` to find users whose `alarm_time` has hit. It sends a "WAKE UP!" Telegram message.
2. Buffer Window: A purely silent delay starts (the "Freshen Up" buffer), allowing the user to get out of bed without staring at their phone.
3. Randomized OTP Drop: When the buffer ends, Celery spins up a random ETA (0 to 10 minutes) and drops a dynamically generated 6-digit OTP into the user's chat.
4. OTP Verification: The user has exactly 2 minutes to reply to the bot with the OTP code. This is verified against hashed Redis TTL keys.
5. Success/Penalty: If the code is correct, the `WakeSession` is marked `VERIFIED`. If the code expires or is incorrect, a penalty task automatically fires, transitioning to `FAILED` and deducting funds via the ledger.

7. Background Task System
-------------------------
Celery drives the completely automated, un-bribable engine:
- `trigger_alarms`: Runs on a cron pulse, cross-referencing local machine time with User database settings.
- `schedule_otp_drops`: Uses Celery's `apply_async` with an absolute `datetime` ETA object to execute dynamically delayed drops.
- `process_penalties`: Cleans up the state-machine. If a WakeSession expires without verification, it mathematically executes the penalty without requiring API intervention.

8. Technology Stack
-------------------
- FastAPI: Chosen for hyper-fast async capabilities and robust dependency injection.
- SQLAlchemy 2.0 (Async): The modern ORM for interacting safely with the database without blocking the event loop.
- SQLite (aiosqlite): Used currently for rapid development and relational constraint mapping.
- Redis (Memurai on Windows): Serves as both the Celery message broker and the ultra-low-latency TTL mechanism for storing temporary 2-minute OTP strings.
- Celery & Celery Beat: The absolute standard for distributed and reliable task queuing and execution.
- Telegram Bot API: The front-end UI interface, keeping friction extremely low for the end-user.
- Python 3.x: The core application language.

9. Design Decisions
-------------------
- Separating Plans from Preferences: Users can freely change their morning alarm time without cancelling or destroying their 7-day financial commitment.
- Ledger Transactions: Replaces typical boolean mutation to create a system that can be mathematically reconciled and audited for financial compliance.
- Redis TTL for OTP: Prevents database bloating. The OTP literally ceases to exist in computational memory the millisecond the 2-minute expiration triggers.
- Idempotency & Locking: Financial transaction tasks process exactly once, preventing race conditions where users could be double-charged.

10. Challenges Faced During Development
---------------------------------------
- Async Event Loop Conflicts: Encountered massive thread-locking when combining `python-telegram-bot` with FastAPI's `asyncio` loop. Solved by bypassing the default `run_polling` method and implementing manual piecemeal polling within FastAPI's `@lifespan` context.
- SQLite Migration Locks: Alembic's `batch_alter_table` struggled uniquely with SQLite's non-transactional DDL operations, specifically regarding foreign key reflections that dropped tables out from underneath the migrations. Solved by intelligently crafting isolated "ghost" tables to bypass schema reflection issues.
- Background Scheduling States: Mapping states cleanly asynchronously across Telegram -> Celery -> DB without race conditions required strict State Machine isolation.

11. Current System Capabilities
-------------------------------
- Full mathematical wallet ledger (Deposit, Withdraw, Plan Lock, Penalty).
- Dynamic Plan generation mapping custom durations to custom locked balances.
- Telegram bot interface capable of receiving commands and plain-text OTP answers.
- Automated Cron Job scheduling triggering daily.
- Interactive UX where alarms dynamically adjust to custom user buffers.

12. Possible Future Improvements
--------------------------------
- Plan Auto-Cleanup Cron: A nightly sweep to resolve exhausted plans and natively transfer surviving locked funds back to available balances.
- Anti-Cheat Cooldowns: Enforcing hard limits on users attempting to change their alarm time purely to dodge an impending verification.
- Timezone Awareness: Moving completely away from localized system time to UTC timestamps across the DB, mapping timezone offsets entirely per user preference.
- External Payment Gateways: Hooking the simulation up to Stripe or PayPal for genuine real-world financial stakes.
- Web Dashboard: A Next.js frontend to visualize the math, the ledger, and the user's historical wake habits via charts.
